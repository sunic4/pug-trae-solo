# pg-fix

## 启动：判断路径

Glob `pg/issues/` 已有产物：

| 已有产物 | 阶段 |
|---|---|
| 无 | phase 1 |
| report.md(confirmed) | phase 2 |
| analysis.md(confirmed) | phase 3 |

路径判定：
- 根因一眼确定 + 改动 1-2 处 + 无跨模块风险 → 快速通道
- 用户说"P0/线上挂了/紧急" → 紧急模式
- 其余 → 标准流程

## Phase 1：问题记录

逐个问（不一次抛多个）：
1. 看到什么现象？
2. 怎么复现？
3. 期望 vs 实际（分开写）
4. 涉及哪个模块？
5. 严重程度（P0-P3）

只记现象，不记根因。写 `{slug}-report.md`。

## Phase 2：根因分析

**必须读代码**，不靠猜：
1. 定位问题代码（grep/读文件）
2. 还原失败路径（正常 vs 失败的分叉点）
3. 确认根因 + 影响面
4. 给 2-3 种修复方案让用户选

写 `{slug}-analysis.md`，用户确认方案后进 phase 3。

## Phase 3：修复验证

约束：
- 只改分析里声明的文件
- 改动最小化，不引入新抽象
- 每处改动后汇报

验证清单：
- 复现步骤验证
- 期望行为验证
- 影响面回归
- 前端改动浏览器验证

写 `{slug}-fix-note.md`（唯一必须文档）。

### 修复收尾推荐

修完后逐条问（用户说"不用"立刻跳过）：

1. 有踩坑值得记？→ 推荐 `pg-doc`(learn)
2. 修复暴露了长期约束/选型？→ 推荐 `pg-doc`(decide)

## 快速通道

简单 bug：直接告知根因 + 方案 → 用户确认 → 修复 → 验证 → 写 fix-note。

## 紧急模式

P0 专用，先止血再补文档：

1. **止血**：最小改动让系统恢复，不追求完美修复
2. **验证**：确认系统恢复运行
3. **补 fix-note**：记录止血措施 + 遗留问题
4. **可选**：根因未明的，建议后续走标准流程补 analysis

紧急模式不写 report 和 analysis，只写 fix-note。止血后如果根因复杂，主动建议用户另起一个标准流程的 issue 深入分析。

## 文件结构

```
pg/issues/YYYY-MM-DD-{slug}/
├── {slug}-report.md    ← phase 1（标准路径）
├── {slug}-analysis.md  ← phase 2（标准路径）
└── {slug}-fix-note.md  ← phase 3 / 快速通道 / 紧急模式（必须）
```
