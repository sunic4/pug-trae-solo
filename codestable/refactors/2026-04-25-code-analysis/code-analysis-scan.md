# 代码分析重构扫描清单

## 总览

本次扫描范围涵盖了项目的核心模块，包括：
- `packages/core/src/app-context.ts` - 应用上下文实现
- `packages/theme/src/theme-context.ts` - 主题系统
- `packages/composer/src/node.ts` - 组件基类
- `packages/components/src/button.ts` - 按钮组件
- `packages/renderer/src/canvas-renderer.ts` - 渲染器实现

扫描发现了 12 个优化点，按分类分布如下：
- L1 行为等价迁移信号：2 个
- L2 代码级重构信号：4 个
- L3 结构拆分信号：3 个
- L4 性能信号：3 个

按风险分布：
- 低风险：7 个
- 中风险：3 个
- 高风险：2 个

建议优先处理的优化点：
1. 移除全局主题上下文依赖（L1，中风险）
2. 统一组件 API 设计（L2，低风险）
3. 优化渲染性能，只绘制脏节点（L4，中风险）
4. 提取公共主题获取逻辑（L3，低风险）

建议谨慎处理的优化点：
1. 重构主题系统为纯依赖注入模式（L1，高风险）
2. 优化类型定义，减少 any 类型使用（L2，高风险）

## 优化点清单

### 1. 移除全局主题上下文依赖

**分类**：L1 行为等价迁移信号
**风险**：中
**文件**：`packages/theme/src/theme-context.ts`
**描述**：当前主题系统仍然依赖全局主题上下文 `globalThemeContext` 和全局 AppContext 引用 `globalAppContext`，这与 AppContext 的依赖注入理念不符。
**建议**：移除全局状态，完全依赖 AppContext 进行主题管理，提供向后兼容的迁移策略。
**影响范围**：所有使用主题的组件
**验证方式**：运行测试套件，确保所有组件仍能正确获取主题

### 2. 统一组件 API 设计

**分类**：L2 代码级重构信号
**风险**：低
**文件**：`packages/components/src/button.ts` 及其他组件
**描述**：组件构造函数同时接受 `appContext` 参数和 `props.appContext`，导致 API 冗余和可能的混淆。
**建议**：统一 API 设计，只从 props 中获取 appContext，或只通过构造函数参数传递。
**影响范围**：所有组件
**验证方式**：运行测试套件，确保组件创建和使用方式正确

### 3. 优化渲染性能，只绘制脏节点

**分类**：L4 性能信号
**风险**：中
**文件**：`packages/renderer/src/canvas-renderer.ts`
**描述**：当前渲染系统总是绘制所有节点，不管是否脏，可能导致不必要的绘制操作。
**建议**：修改 `drawAllNodes` 方法，只绘制脏节点，提高渲染性能。
**影响范围**：渲染系统
**验证方式**：运行性能测试，比较优化前后的渲染速度

### 4. 提取公共主题获取逻辑

**分类**：L3 结构拆分信号
**风险**：低
**文件**：`packages/components/src/button.ts` 及其他组件
**描述**：每个组件都实现了 `getTheme()` 方法，代码重复。
**建议**：提取公共主题获取逻辑到工具函数或基类中，减少代码重复。
**影响范围**：所有组件
**验证方式**：运行测试套件，确保组件仍能正确获取主题

### 5. 优化类型定义，减少 any 类型使用

**分类**：L2 代码级重构信号
**风险**：高
**文件**：`packages/composer/src/node.ts`
**描述**：`ComposeNodeProps` 使用了 `[key: string]: any` 类型定义，不够严格。
**建议**：使用更严格的类型定义，避免使用 any 类型。
**影响范围**：所有组件
**验证方式**：运行 TypeScript 类型检查，确保没有类型错误

### 6. 完善错误处理

**分类**：L2 代码级重构信号
**风险**：低
**文件**：`packages/renderer/src/canvas-renderer.ts`
**描述**：获取 canvas 上下文时的错误处理比较简单，缺乏详细的错误信息。
**建议**：增强错误处理，提供更详细的错误信息。
**影响范围**：渲染系统
**验证方式**：测试 canvas 不可用的情况，确保错误处理正确

### 7. 优化 AppContext 类型定义

**分类**：L2 代码级重构信号
**风险**：低
**文件**：`packages/core/src/app-context.ts`
**描述**：`AppContext` 接口中 `renderer` 属性为 `Renderer | undefined`，但在实现中使用了 `Renderer | null`。
**建议**：统一类型定义，使用一致的类型。
**影响范围**：核心系统
**验证方式**：运行 TypeScript 类型检查，确保没有类型错误

### 8. 优化组件树中 AppContext 传递

**分类**：L3 结构拆分信号
**风险**：低
**文件**：`packages/composer/src/node.ts`
**描述**：当前 `addChild` 方法中只在子节点没有 appContext 且父节点有 appContext 时才传递，逻辑不够清晰。
**建议**：优化 appContext 传递逻辑，确保组件树中 appContext 的一致性。
**影响范围**：组件系统
**验证方式**：运行测试套件，确保 appContext 正确传递

### 9. 优化渲染循环

**分类**：L4 性能信号
**风险**：低
**文件**：`packages/renderer/src/canvas-renderer.ts`
**描述**：当前渲染循环总是请求下一帧，即使没有脏矩形。
**建议**：优化渲染循环，只有在有脏矩形时才请求下一帧。
**影响范围**：渲染系统
**验证方式**：运行性能测试，比较优化前后的性能

### 10. 重构主题系统为纯依赖注入模式

**分类**：L1 行为等价迁移信号
**风险**：高
**文件**：`packages/theme/src/theme-context.ts`
**描述**：当前主题系统混合使用依赖注入和全局状态，导致依赖关系不清晰。
**建议**：重构主题系统为纯依赖注入模式，完全移除全局状态。
**影响范围**：所有使用主题的组件
**验证方式**：运行测试套件，确保所有组件仍能正确获取主题

### 11. 优化组件更新逻辑

**分类**：L4 性能信号
**风险**：低
**文件**：`packages/composer/src/node.ts`
**描述**：当前 `markLayoutDirty` 方法总是向上标记父节点为布局脏，可能导致不必要的布局计算。
**建议**：优化布局脏标记逻辑，只在必要时向上标记父节点。
**影响范围**：组件系统
**验证方式**：运行性能测试，比较优化前后的布局计算性能

### 12. 完善文档和注释

**分类**：L2 代码级重构信号
**风险**：低
**文件**：所有核心文件
**描述**：一些代码缺乏注释，特别是复杂的逻辑部分。
**建议**：添加详细的注释和文档，提高代码可读性。
**影响范围**：所有核心模块
**验证方式**：代码审查，确保注释和文档完整
